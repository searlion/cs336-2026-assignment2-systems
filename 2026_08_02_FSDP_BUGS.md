## Bug 1 — replicated parameters never had their gradients synchronized

This is what both failing assertions were pointing at.

### Original code

```python
    def finish_gradient_synchronization(self):
        pass
```

### Why it is a bug

FSDP only shards `Linear` and `Embedding` weights. Everything else — in `ToyFSDPModel` that
means `norm1.weight` and `norm2.weight` (`RMSNorm`) — stays **fully replicated** on every rank.

Replicated parameters start out identical across ranks, but each rank runs backward on only its
own slice of the batch, so after `loss.backward()` each rank holds a *different partial*
gradient. Nothing ever combined them:

- The **sharded** parameters were already fine — `reduce_scatter_grad` scales by
  `1 / world_size` and reduce-scatters with `ReduceOp.SUM`, which performs the cross-rank
  averaging as a side effect of distributing the shards.
- The **replicated** parameters had no collective at all. `finish_gradient_synchronization`,
  which `fsdp_on_after_backward` calls precisely to close this gap, was a no-op.

That explains both symptoms exactly:

- `test_fsdp_gradient_sync` all-gathers `norm1.weight.grad` and compares across ranks. Rank 0's
  gradient came from its 4 sequences and rank 1's from 4 different sequences, so they disagreed
  by 28.4 — they were never reduced.
- `test_fsdp_correctness` compares against a single-process baseline trained on the *full*
  20-sample batch. Each FSDP rank stepped SGD with its local 10-sample gradient instead of the
  global one, so after one step the parameters had drifted by `lr × (grad difference)`
  ≈ `0.01 × 0.083` ≈ `8.3e-4` — matching the reported max diff on step 0.

### Fix

Two parts. First, in `__init__`, record which parameters FSDP actually sharded (`FSDP.py:145`):

```python
        # Parameters FSDP sharded; everything else is replicated and needs DDP-style
        # gradient averaging in finish_gradient_synchronization().
        self._sharded_param_ids = {id(rec.owner_module.weight_shard) for rec in self.metadata_record.values()}
```

Then implement the synchronization (`FSDP.py:171`):

```python
    def finish_gradient_synchronization(self):
        """Average the gradients of the *replicated* (non-sharded) parameters.

        Sharded parameters already had their gradients averaged by the reduce-scatter
        in `reduce_scatter_grad`. Replicated parameters (RMSNorm weights, biases, ...)
        are identical on every rank, but each rank only saw its own slice of the batch,
        so their gradients are per-rank partial results and must be all-reduced with a
        mean, exactly like DDP does.
        """
        handles = []
        for p in self.module.parameters():
            if id(p) in self._sharded_param_ids or p.grad is None:
                continue
            p.grad.div_(self.world_size)
            handles.append(dist.all_reduce(p.grad, op=dist.ReduceOp.SUM, async_op=True))
        for handle in handles:
            handle.wait()
```

### Why the fix works

Each rank's loss is a mean over its `local_bs` samples, so its gradient is the mean gradient
over its own slice. With equal local batch sizes, the mean of the per-rank means equals the mean
over the global batch — which is exactly what the single-process baseline computes. Dividing by
`world_size` before a `SUM` all-reduce produces that mean, and leaves every rank holding the
identical result, so the replicated parameters stay bit-identical across ranks as training
proceeds. This is the same thing DDP does for every parameter; FSDP just needs it only for the
parameters it did not shard.

Implementation notes:

- The division happens **before** the collective because gloo does not support
  `dist.ReduceOp.AVG` (it is NCCL-only). `div_` then `SUM` is the portable equivalent.
- Sharded parameters are identified by **object identity** (`id(p) in self._sharded_param_ids`)
  rather than by a `name.endswith("weight_shard")` string test. The name test would silently
  skip a user parameter that happened to be named `weight_shard`, and would depend on the naming
  convention rather than on what was actually sharded.
- `async_op=True` lets the per-parameter all-reduces overlap instead of serializing; the
  `handle.wait()` loop at the end is what guarantees the gradients are final before
  `optimizer.step()` runs.
- `self.module.parameters()` yields in a deterministic, structure-derived order that is identical
  on every rank, so the collectives are issued in the same order everywhere — required, since
  mismatched collective ordering deadlocks.

## Bug 2 — `compute_dtype` was accepted and stored but never used

### Original code

`compute_dtype` was saved in `__init__`:

```python
        self.compute_dtype = compute_dtype
```

...and then read nowhere. The all-gather buffer was allocated in the shard's own dtype:

```python
    def all_gather_full_tensor(self, mods: nn.Module, args: Any = None) -> None:
            metadata_record = self.metadata_record[mods]
            numel = metadata_record.shard_numel*self.world_size
            if metadata_record.gathered_full_tensor is None:
                metadata_record.gathered_full_tensor = torch.empty(numel, dtype=mods.weight_shard.dtype, device=mods.weight_shard.device)
            # We store the full_weight_instead of full_weight unpadded so that when we apply resize_(0), it works with the original reference and not the view()
            full_weight = metadata_record.gathered_full_tensor
            _alloc_storage(full_weight)
            with _preserve_vc(full_weight):
                dist.all_gather_into_tensor(output_tensor=full_weight, input_tensor=mods.weight_shard.detach(), async_op=False)
```

Since `weight_shard` is fp32, the gathered parameter was fp32 and forward/backward always ran in
full precision, regardless of what the caller asked for.

### Why it is a bug

The `fp16` parametrization builds its baseline with `_apply_mixed_precision_hooks`, which casts
`Linear`/`Embedding` weights to `compute_dtype` for forward and backward while keeping the master
weights and the optimizer update in fp32. The test then asserts the FSDP model matches that
baseline to `atol=1e-4, rtol=1e-4`.

Running everything in fp32 is *more* accurate than the baseline — but the test is a **match**
check, not an accuracy check, and fp16 rounding in the baseline's matmuls is well above 1e-4
relative. Confirmed empirically by reverting only this line:

```
FAILED test_fsdp_correctness[fp16] - Step 0: Parameter linear1.weight mismatch. Max diff: 0.00021661
```

`2.2e-4 > atol=1e-4`. This bug was masked in the original run because bug 1 aborted the fp16 test
at `norm1.weight` before it ever reached a sharded parameter.

Beyond the test, ignoring `compute_dtype` also throws away the feature's real benefit: the
all-gather is the dominant FSDP communication cost, and gathering in fp16 halves it.

### Fix

`FSDP.py:45-56`:

```python
            shard = mods.weight_shard
            # Master weights (the shard) stay in fp32; the gathered copy that forward/backward
            # actually compute with lives in compute_dtype when mixed precision is requested.
            gather_dtype = self.compute_dtype if self.compute_dtype is not None else shard.dtype
            if metadata_record.gathered_full_tensor is None:
                metadata_record.gathered_full_tensor = torch.empty(numel, dtype=gather_dtype, device=shard.device)
            full_weight = metadata_record.gathered_full_tensor
            _alloc_storage(full_weight)
            send = shard.detach().to(gather_dtype)
            with _preserve_vc(full_weight):
                dist.all_gather_into_tensor(output_tensor=full_weight, input_tensor=send, async_op=False)
```

### Why the fix works

This establishes the standard mixed-precision split:

- `weight_shard` — the **master weight**, and the only thing the optimizer sees — stays fp32.
  Optimizer state and the parameter update keep full precision, which is what prevents small
  updates from being lost to fp16 rounding over many steps.
- `gathered_full_tensor` — the transient full parameter that forward and backward actually
  compute with — is allocated in `compute_dtype`. `param_view` is a view into that buffer, so it
  inherits fp16, and every consumer downstream (the `einsum` in `Linear`, the row gather in
  `Embedding`) now runs in fp16, exactly matching what the baseline's hooks do to `m.weight.data`.
- `shard.detach().to(gather_dtype)` performs the down-cast on the way into the collective, so the
  wire payload is fp16 too.

The return path already handled its half correctly and needed no change: because `param_view` is
fp16, autograd produces an fp16 `.grad`, and `reduce_scatter_grad`'s existing
`out = out.to(shard.dtype)` up-casts back to fp32 before assigning to `weight_shard.grad`. That is
what satisfies `test_fsdp_gradient_sync`'s `param.grad.dtype == param.data.dtype` assertion, and
what keeps the SGD update itself in fp32.

Note that `RMSNorm` is deliberately left in fp32 — it is neither `Linear` nor `Embedding`, so FSDP
never touches it, which matches the baseline's hooks (they only iterate `Linear`/`Embedding`).
`RMSNorm.forward` internally up-casts its input to fp32 and casts the result back to the input
dtype, so its weight gradient arrives as fp32 and the dtype assertion holds there too.

## Bug 3 — unconditional `delattr`, and the backward pre-hook's `weight` left dangling (latent)

### Original code

```python
    def free_full_tensor(self, mods: nn.Module, args: Any = None, output: Any = None) -> None:
        metadata_record = self.metadata_record[mods]
        _free_storage(metadata_record.gathered_full_tensor)
        delattr(mods, metadata_record.owner_attribute_name)
```

### Why it is a bug

Two related problems, both about the lifetime of the temporary `mods.weight` attribute.

**The backward path is unbalanced.** Three hooks are registered per sharded module:

```python
                mods.register_forward_pre_hook(self.all_gather_full_tensor)
                mods.register_forward_hook(self.free_full_tensor)
                mods.register_full_backward_pre_hook(self.all_gather_full_tensor)
```

The forward path is symmetric: the pre-hook does `setattr(mods, "weight", param_view)` and the
post-hook deletes it. The backward path is not — the backward pre-hook re-installs
`mods.weight`, but nothing removes it. Meanwhile `reduce_scatter_grad` ends with
`_free_storage(metadata_record.gathered_full_tensor)`, resizing the underlying storage to 0.

So from the end of `backward()` until the next forward pre-hook, every sharded module holds a
`weight` attribute pointing at a tensor whose storage has size 0 — a live handle to freed memory.
It did not fail these tests only because the next forward pre-hook re-allocates before anything
reads it. Any code that touches `mods.weight` in that window — a debug print, a `state_dict()`
call, a gradient-clipping pass, an inspection in a notebook — sees a zero-size tensor with the
right shape metadata.

**The `delattr` is unguarded.** `delattr` raises `AttributeError` if the attribute is not present.
Any path where `free_full_tensor` runs without a matching `setattr` — an exception between hooks,
or now the extra delete added in `reduce_scatter_grad` — turns into a hard crash rather than a
no-op.

### Fix

`FSDP.py:67-71` — guard the delete:

```python
    def free_full_tensor(self, mods: nn.Module, args: Any = None, output: Any = None) -> None:
        metadata_record = self.metadata_record[mods]
        _free_storage(metadata_record.gathered_full_tensor)
        if metadata_record.owner_attribute_name in mods.__dict__:
            delattr(mods, metadata_record.owner_attribute_name)
```

`FSDP.py:94-98` — and close the backward path, right where the storage is freed:

```python
        _free_storage(metadata_record.gathered_full_tensor)
        # Drop the stale `weight` attribute the backward pre-hook re-installed; it now
        # points at storage of size 0.
        owner = metadata_record.owner_module
        if metadata_record.owner_attribute_name in owner.__dict__:
            delattr(owner, metadata_record.owner_attribute_name)
```

### Why the fix works

Deleting the attribute in the same place the storage is freed makes the invariant local and
checkable: **`mods.weight` exists if and only if `gathered_full_tensor` has live storage.** Both
paths that free now also unset, so the module is never observable in the freed-storage state.

Checking `in mods.__dict__` (rather than `hasattr`) is the right test here because the temporary
is a plain tensor assigned via `object.__setattr__` — `weight` was removed from the module's
`_parameters` dict back in `__init__` by `delattr(mods, "weight")`, so `nn.Module.__setattr__`
falls through to a normal instance attribute. `hasattr` would also consult the class and its
bases; `__dict__` asks precisely "is the instance attribute set right now", which is the
condition that makes `delattr` safe. The guard makes both deletes idempotent, so neither ordering
of hooks nor an early exception can turn cleanup into a crash.

## Not a bug: the `world_size=3` failure in `_scratch_fsdp.py`

`distributed_training/_scratch_fsdp.py` runs `_test_fsdp_correctness` with `world_size=3` and
reports a mismatch even with all three bugs fixed. That is a harness artifact, not an FSDP defect.

`_test_fsdp_correctness` hardcodes `batch_size = 20` and splits with
`local_bs = batch_size // world_size`. At `world_size=3` that is 6, so the ranks cover samples
0–17 and **two samples are silently dropped**; the mean of three 6-sample means is not the
20-sample mean the single-process baseline computes. The comparison is invalid by construction at
any world size that does not divide 20.

Use a world size that divides 20. `world_size=5` is the informative one, because 5 both divides
the batch **and** produces jagged shards — `linear1.weight` has `128 × 64 = 8192` elements, and
`ceil(8192 / 5) = 1639` with `5 × 1639 = 8195`, so 3 elements of padding exercise the
`clamp_jagged_tensor_size` path. (`world_size=4` divides the batch but every weight divides
evenly, so it never tests padding at all.) Verified passing:

```
OK world_size=5 dtype=None            _test_fsdp_correctness
OK world_size=5 dtype=torch.float16   _test_fsdp_correctness
OK world_size=3 dtype=None            _test_fsdp_gradient_sync
OK world_size=3 dtype=torch.float16   _test_fsdp_gradient_sync
OK world_size=5 dtype=None            _test_fsdp_gradient_sync
OK world_size=5 dtype=torch.float16   _test_fsdp_gradient_sync
```

`_test_fsdp_gradient_sync` does not compare against a full-batch baseline, so it is valid at any
world size — which is why `world_size=3` is still a useful padding test there.

## Left alone deliberately

- **`UserWarning: Full backward hook is firing when gradients are computed with respect to module
  outputs since no inputs require gradients.`** Expected, and emitted only for `Embedding`, whose
  input is integer token IDs so no input requires grad. The pre-hook still fires when the gradient
  w.r.t. the module *output* is computed, which is all that is needed to re-gather the weight
  before the embedding backward runs. (It surfaces despite `@pytest.mark.filterwarnings("error")`
  because it is raised inside `mp.spawn`ed child processes, which do not inherit pytest's warning
  filters.)
- **`Record.work_handle` is unused.** The reduce-scatter is issued synchronously
  (`async_op` defaults to `False`). Making it async and waiting on the handles in
  `finish_gradient_synchronization` would overlap gradient communication with the rest of the
  backward pass — a performance improvement, not a correctness fix.
